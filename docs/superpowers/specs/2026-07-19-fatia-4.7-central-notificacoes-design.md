# Fatia 4.7 — Central de notificações in-app

## Objetivo

Sino no header com badge de não lidas, alimentado pelos mesmos eventos que já disparam push hoje.
Cobre os 7 pontos de disparo existentes: chat (nova mensagem), comida (novo pedido + chegou),
comunicado (novo), reserva (nova pendente + aprovada/cancelada), assembleia (nova/aviso),
encomenda (chegou).

## Tabela `notificacoes` (nova migration)

Uma linha por (evento, destinatário) — não é junção estilo `comunicado_leituras`, porque cada
notificação já nasce endereçada a um usuário só, igual às linhas de `device_tokens`/push atuais.

```
id              uuid, PK, default gen_random_uuid()
condominio_id   uuid, not null, references condominios, ON DELETE CASCADE
user_id         uuid, not null, references users, ON DELETE CASCADE
tipo            text, not null, check IN ('chat','comida','comunicado','reserva','assembleia','encomenda')
titulo          text, not null
corpo           text, not null
referencia_id   uuid, not null   -- id da entidade (comidaId, comunicadoId, etc.)
lida            boolean, not null, default false
created_at      timestamptz, not null, default now()
```

Índices: `condominio_id`, `(user_id, lida)`. RLS: mesma policy de tenant isolation por
`condominio_id` usada em `device_tokens`.

## Backend

**`notificationService.ts`** ganha `notifyUsers(ctx, userIds, { tipo, titulo, corpo, referenciaId })`:
insere uma linha em `notificacoes` por `userId`, depois chama `sendPushToTokens` com os tokens
desses mesmos usuários (busca via `listTokensForUsers`, já usado nos call sites atuais). Best-effort
igual push: falha ao gravar notificação não pode derrubar a operação principal (create de
comunicado/encomenda/etc.) — mesma postura defensiva do `sendPushToTokens` atual (nunca lança).

As 7 chamadas atuais de `sendPushToTokens` nos controllers trocam para `notifyUsers`, passando os
mesmos `userIds` que hoje viram `tokens` via `listTokensForUsers`/`listTokensForCondominio`:

- `chatController.ts` — destinatários (admins ou o morador da thread)
- `comidaController.ts` (create) — porteiros
- `comidaController.ts` (status chegou) — morador do pedido
- `comunicadoController.ts` — todos do condomínio
- `reservaController.ts` (create) — admins
- `reservaController.ts` (status) — morador da reserva
- `assembleiaController.ts` (`notificarMoradores`) — moradores

`listTokensForCondominio`/`listTokensForUsers` continuam existindo (uso interno de `notifyUsers`
pro push); a diferença é que agora o controller passa `userIds` pra `notifyUsers` em vez de
`tokens` direto pra `sendPushToTokens`. Onde o controller só tinha a lista de tokens sem os
userIds (nenhum caso hoje — todos já resolvem userIds antes de buscar tokens), não se aplica.

**Model `Notificacao.ts`** (novo, `apps/backend/src/models/`): `createNotificacoes`,
`listNotificacoes(ctx, userId, { apenasNaoLidas, limit })`, `countNaoLidas(ctx, userId)`,
`marcarComoLida(ctx, userId, id)`, `marcarTodasComoLidas(ctx, userId)`.

**Controller `notificacaoController.ts`** (novo) + rotas em `apps/backend/src/routes/`:

- `GET /notificacoes?apenasNaoLidas=true` — lista as últimas 20, mais recentes primeiro
- `GET /notificacoes/nao-lidas/contagem` — `{ contagem: number }`, usado pelo polling do badge
- `PATCH /notificacoes/:id/lida` — marca uma como lida
- `PATCH /notificacoes/lidas` — marca todas como lidas

Todas as rotas exigem auth (qualquer role logada), sem `roles` restrito — cada usuário só vê as
próprias (filtro por `user_id = req.user!.id` no model, dentro do tenant).

## Frontend

**`services/api/types.ts`**: tipo `Notificacao` espelhando a tabela (camelCase). **`services/api/`**:
novo módulo `notificacoes.ts` com as 4 chamadas.

**`components/Layout/NotificationBell.tsx`** (novo), colocado no `Header.tsx` entre `Logo`/nav e
`ThemeToggle`. Estrutura:

- Botão sino (`BellIcon` novo em `components/ui/icons`) com badge numérico no canto superior
  direito quando `contagem > 0` (mostra "9+" acima de 9). Mesma paleta de destaque usada em outros
  badges do design system.
- Contagem buscada no mount e via `setInterval` de 30s (`GET /notificacoes/nao-lidas/contagem`);
  limpa o interval no unmount.
- Clique no sino abre dropdown (painel posicionado abaixo, alinhado à direita — reaproveita o
  padrão visual de overlay leve já usado em menus existentes; fecha ao clicar fora ou ESC).
  Dropdown busca a lista completa (`GET /notificacoes`) na abertura.
- Cada item: título, corpo truncado a 1 linha, tempo relativo (ex. "há 5 min"), indicador visual
  de não lida (ponto/realce). Lista vazia mostra estado vazio simples ("Nenhuma notificação").
- Clique num item: marca como lida (otimista, sem re-fetch bloqueante) + `navigate()` pra rota do
  tipo + fecha dropdown. Mapa `tipo → rota`: `chat→/chat`, `comida→/comida`,
  `comunicado→/comunicados`, `reserva→/areas-comuns`, `assembleia→/assembleias`,
  `encomenda→/encomendas`.
- Botão "Marcar todas como lidas" no topo do dropdown, visível só quando há não lidas; chama
  `PATCH /notificacoes/lidas`, zera badge e atualiza indicadores da lista aberta.

## Fora de escopo

- Websocket/SSE — polling de 30s é o mecanismo de atualização, mesmo padrão (ausência de infra
  real-time) do resto do app hoje.
- Preferências de notificação (silenciar tipo X) — tudo que dispara push também vira notificação
  in-app, sem opt-out granular.
- Paginação além das últimas 20 / histórico completo — sem tela dedicada de notificações por
  enquanto (pode virar fatia futura se volume justificar).
- Expiração/limpeza automática de notificações antigas.

## Testes manuais

Gerar cada um dos 7 eventos (via os fluxos já existentes: mandar chat, pedir comida, marcar comida
como chegou, criar comunicado, criar reserva, aprovar/cancelar reserva, criar assembleia) e
confirmar: badge incrementa, push continua chegando como antes, item aparece no dropdown, clique
marca lida + navega, "marcar todas" zera badge. Testar em claro/escuro e com múltiplos usuários
(destinatário certo recebe, outros não).
