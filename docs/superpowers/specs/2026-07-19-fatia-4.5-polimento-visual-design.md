# Fatia 4.5 — Polimento visual (design)

Roadmap: `docs/roadmap.md` linhas 48-50. Bloco A (Fundação de UX), última fatia antes do drawer
de detalhe (4.6).

## Escopo

1. Ícones faltantes na nav (Dashboard, grupo Cadastros)
2. Empty states ilustrados com CTA de criação
3. Skeleton loading — auditoria de consistência
4. Espaçamento/grid — auditoria geral nas telas de listagem
5. Teste claro/escuro de tudo acima

Fora de escopo: drawer de detalhe (4.6), central de notificações (4.7), qualquer módulo novo do
Bloco C.

## 1. Ícones de nav

Criar em `apps/web/src/components/ui/icons.tsx`, seguindo o helper `base()` existente (outline,
stroke 2, viewBox 24, `currentColor`):

- `DashboardIcon` — grid/painel (referência: 4 quadrados ou barras de gráfico simples)
- `ResidenciaIcon` — prédio/porta (item "Residências")
- `MoradorIcon` — pessoa (item "Moradores"; reaproveitar ícone de usuário existente em
  `icons.tsx` se já houver um genérico, senão criar)
- `EquipeIcon` — dois usuários/crachá (item "Equipe")
- `PermissaoIcon` — escudo/cadeado (item "Permissões")
- `CondominioIcon` — prédios/skyline (item "Condomínios")

Ligar cada um via `icon: XIcon` nas entradas correspondentes de `NAV_ITEMS` em
`apps/web/src/components/Layout/Nav.tsx` (linhas 31, 68-72). Sem mudança de estrutura no `Nav.tsx`
— a renderização condicional (`item.icon && <item.icon .../>`) já existe.

## 2. Empty states ilustrados + CTA

Para as 6 telas com `EmptyState` (Solicitações, Encomendas, Visitantes, Comida, Áreas Comuns,
Moradores):

- Substituir o ícone único 48px por uma ilustração SVG dedicada por módulo, ~120-160px, usando
  só cores dos tokens (`primary`/`accent`/`text-muted` via `currentColor`/CSS vars) — nunca hex
  hardcoded.
- `action` do `EmptyState` passa a ser sempre preenchido:
  - Zero itens sem filtro ativo → CTA abre o form de criação já existente do módulo (todas as 6
    telas já têm: `CreateSolicitacaoForm`, `CreateEncomendaForm`, `CreateVisitanteForm`,
    `CreateComidaForm`, `CreateAreaComumForm`, `CreateMoradorForm`).
  - Filtro ativo e zero resultado → mantém CTA "Limpar filtros" (comportamento atual, sem
    regressão).
- Componente `EmptyState.tsx` ganha suporte a receber a ilustração maior no lugar do ícone atual
  (prop `icon` continua `ReactNode`, só muda o que cada tela passa).

## 3. Skeleton loading — auditoria de consistência

Sem componente novo. `Skeleton.tsx` e a animação `skeleton-pulse` já estão corretos.

- Páginas com `DataTable` (Solicitações, Encomendas, Visitantes, Comida, Áreas Comuns, Moradores):
  já usam skeleton linha-a-linha via prop `loading`/`skeletonRows` — manter.
- Páginas sem tabela que usam `Skeleton` manualmente (Chat, Assembleias, Dashboard, Comunicados,
  Residências, Equipe, Condomínios): auditar cada uma; `PermissoesPage.tsx` hoje usa um skeleton
  único cobrindo a página toda (diferente do padrão estruturado header+linhas das demais) —
  padronizar pra ficar consistente com o resto.

## 4. Espaçamento/grid — auditoria geral

Nas 6 telas de listagem (`ListToolbar` + `DataTable` + `Pagination` dentro do card único):

- Checar largura máxima do container e se sobra espaço vazio lateral.
- Checar distribuição de colunas do `DataTable` (colunas estreitas demais vs. espaço sobrando).
- Checar padding vertical entre `ListToolbar` e a tabela, e padding interno do card.
- Ajustes só via classes Tailwind existentes (escala 4/8/12/16/24/32px do Design System), sem
  mudar a estrutura dos componentes (`DataTable`/`ListToolbar`/`Pagination` continuam genéricos).

## 5. Teste claro/escuro

Passar as 6 telas + nav atualizada + empty states novos nos dois modos (`data-theme="dark"` via
`useTheme`), conferindo:

- Ícones novos herdam cor corretamente (usam `currentColor`, sem cor fixa).
- Ilustrações novas usam tokens/CSS vars, sem hex hardcoded — contraste ok nos dois modos.

## Testes

Sem lógica de negócio nova (é polimento visual). Verificação manual nos dois temas é suficiente;
não há teste automatizado a escrever para SVGs/CSS. Se algum ajuste de `EmptyState` mudar
comportamento de prop (`action` sempre presente), conferir que os testes existentes que montam
`EmptyState`/`DataTable` (se houver) continuam passando.
